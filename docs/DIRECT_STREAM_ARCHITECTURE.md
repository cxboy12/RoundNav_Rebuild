# RoundNav Direct 实施方案

1. 在 `carwithin-fork/` 保存固定上游版本的开发副本。新增 `RoundNav ESP32` 输出模式，在 `NativeReceiver` 实际视频分发处接入，首版请求 H.264。VideoToolbox 收到连续 access unit，SPS/PPS 更新或输入积压时等下一张 IDR 并请求关键帧。
2. 解码后独立处理最新 CVPixelBuffer，按固定图案核对居中裁切、等比适配、方向和圆外黑色。输出首选 360×360、30 FPS、20 KiB 左右，质量约 0.7 起步并做实机对照。检查实际 JPEG SOF 和分量采样因子以及 ESP32 解码。Core Image 质量和 Pillow 质量需要实测匹配。
3. 发送队列采用至多一帧待发、两帧待 ACK。独立匹配帧号和计时，握手、写入或 ACK 超时后关闭旧连接并重连。握手宣告 16 对齐的 CO5300 基准接收器可用 352×352 验证；精确 360×360 的接收端应宣告经过验证的对齐能力。
4. ST77916 固件使用与现有 `ESP32/` BLE 工程不同的子目录，避免 Windows 大小写目录冲突。沿用 DiPlay Wi-Fi、TCP、块解码和 DMA 架构。面板适配以实际开发板型号、接口、引脚、初始化序列、颜色字节序和偏移为输入。第一版 ESP32 AP 地址拟用 `192.168.4.1:7000`，SSID 按 `RoundNav-XXXX` 配置。
5. 依次验证主机协议、iOS 构建与签名、JPEG 样本/固件完整接收、DMA 提交、圆屏实际画面。使用公开固定路线做室内模拟。检查 iPhone 关联和地址、局域网访问、蜂窝数据、锁屏、切页、断线重连以及温升。10/15/20/25/30 FPS 每档至少 10 分钟，最终连续 30 分钟。记录源帧率、解码/缩放/编码/发包时间、字节数、接收/丢弃/显示帧率、解码和刷屏耗时、往返、剩余内存。
6. 只有兼容 JPEG 无法达到稳定目标时，才测量 ESP32 软件 H.264 解码和内存压力，再比较原始 Annex B、iOS 转码 H.264 和现成仪表协议。运行时验收仅使用 iPhone 与 ESP32-S3。

当前证据是电脑中转、固件和 CarWithin 的源码审计及用户提供的历史数据。目标板型号和映射尚待确认，iOS 构建、真机 JPEG、目标固件和端到端性能尚待验证。
